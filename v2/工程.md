## 1. 结论
1. 【事实】Studio 环境足够：macOS 27.0.1，arm64，内存 96 GiB，系统盘剩 962 GiB；已装 Node v26.4.0、Python 3.14.3、sqlite3 3.54.0、codex-cli 0.146.0。
2. 【事实】**阻塞项：gpt-6.1-sol 这个模型被拒了。** 02:2x 做的一次只读测试（`codex exec --sandbox read-only -m gpt-6.1-sol -c model_reasoning_effort=high "Reply OK"`）返回 400，原文如下：
   `The 'gpt-6.1-sol' model is not supported when using Codex with a ChatGPT account.`
   CLI 同时提示 `Model metadata for 'gpt-6.1-sol' not found`。整个调用约 21.7 秒，直到报错，没有拿到有效回复的延迟数据。Studio 上 `~/.codex/config.toml` 里已经配了 `model = "gpt-6.1-sol"`、`model_reasoning_effort = "high"`。
3. 【推断】OpenAI 官方定价页写的是 Plus 及以上套餐可用 GPT-6.1 Sol，Free/Go 套餐不行。被拒的原因可能是：该账号的套餐不含此模型；CLI 版本 0.146.0 太旧，不认识这个模型；或者模型标识写法不对。要等用户确认套餐，并决定要不要升级 CLI（升级会改动 Studio，需要另行授权）。
4. 【建议】技术栈用 Node（Fastify + better-sqlite3 + ts-fsrs）加轻量前端（Vite + Vue 或原生 TS）。AI 内容以**整表批量预生成、存进 SQLite** 为主，在线调用只做偶尔的讲解，并加缓存。没有 AI 也必须能完整背单词，AI 只是锦上添花。

## 3. codex exec 可行性
- **调用方式**【事实，来自 `codex exec --help`】：`-m/--model`、`-c model_reasoning_effort=high`、`-s/--sandbox read-only`、`--json`（输出 JSONL 事件）、`-o/--output-last-message <文件>`、`--output-schema <JSON Schema 文件>`（约束最终回复的格式）、`--ephemeral`（不落会话文件）、`--skip-git-repo-check`、`--ignore-user-config`；prompt 也可以从 stdin 读入。
  - 【建议】后端调用固定为：`codex exec --ephemeral --skip-git-repo-check -s read-only -m <模型> -c model_reasoning_effort=<强度> --output-schema schema.json -o out.json -`，工作目录放在一个空的专用目录里，prompt 从 stdin 传入。
- **延迟**：【事实】这次调用从启动到报错约 21.7 秒，过程中还会加载 skills（有提示说 skills 描述被截短了）。【推断】正常的 high 推理加上 CLI 启动，每次在十几秒到一分钟之间，不适合放在交互流程里同步等待。【待实测】模型可用后，测"Reply OK"和"一个单词的完整内容包"这两种请求的耗时。
- **订阅用量限制**【事实，来源：OpenAI Codex Pricing，https://developers.openai.com/codex/pricing ，核验于 2026-10-17】：
  - Plus 套餐用 GPT-6.1 Sol，每 5 小时大约 15–160 条本地消息，可能还有周限额；Pro 目前没有 5 小时限制；GPT-6 Luna 在 Plus 上是 350–3000 条。官方写明这只是估算、不是固定额度，实际以 usage dashboard 或 CLI 里的 `/status` 为准。
  - `codex exec` 和脚本化工作流都包含在各付费套餐里；超出额度后可以买 credits（会产生费用，需要用户授权）。
  - 【推断】1600 个词如果一个词调一次，在 Plus 套餐下要用掉很多个 5 小时窗口。所以应该**一次调用处理 20–50 个词**，总共大约 40–80 次调用，分几天在夜里跑完。
- **并发**：【建议】后端只开一个任务队列，并发数为 1，所有 codex 调用串行执行；失败后按指数退避重试，最多 3 次；遇到用量超限就暂停到下一个窗口。
- **失败处理**：【建议】每次结果都用 JSON Schema 校验，不合格就丢弃并记进 `ai_jobs` 表；单次超时 180 秒（【待实测】）；在线讲解失败时显示"暂时无法讲解"，背词流程不受影响；人工抽查 5% 预生成的例句。
- **预生成内容**：【建议】每个词生成 2 条例句（初中难度，附中文）、1 条助记、3 道题（英选中、中选英、听音选词的干扰项）。在线调用只在孩子点"再讲讲"时触发，结果按 (词, 问题哈希) 缓存。
- **备选**：【推断】如果 gpt-6.1-sol 一直不能用，可以改用套餐里可用的模型（比如 GPT-6 Luna，额度高很多），或者用 Studio 本地的 Ollama / llama-server（【事实】11434 和 8080 端口都在监听），不花额外的钱。

## 4. SQLite 表结构（概要）
- `words`(id, headword, phonetic, pos, meaning_zh, source[课标2022/人教九年级], unit, freq_rank)
- `word_content`(word_id, kind[example/mnemonic/quiz], body_json, model, prompt_version, created_at, reviewed)
- `cards`(id, word_id, mode[认词/拼写/听音], **FSRS 字段：due, stability, difficulty, elapsed_days, scheduled_days, reps, lapses, state, last_review**)
- `review_logs`(id, card_id, rating, state, due, stability, difficulty, elapsed_days, scheduled_days, review_at, duration_ms)
- `ai_jobs`(id, kind, payload_hash, status, attempts, error, started_at, finished_at)
- `ai_cache`(key_hash, word_id, question, answer, created_at)
- `settings`(key, value)：每日新词数、复习上限、发音偏好等
- 【建议】FSRS 字段名和 ts-fsrs 的 Card/ReviewLog 结构保持一致，以后换成 py-fsrs 也能直接迁移。
